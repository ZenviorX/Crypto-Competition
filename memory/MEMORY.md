# Crypto-Competition 项目记忆协议

状态：Canonical

本目录是 `ZenviorX/Crypto-Competition` 的项目内置记忆库。处理项目任务时，先核验仓库当前真实代码，再使用这里的记忆；记忆不得替代实际代码、测试、Git 状态或命令输出。

## 目录职责

- `MEMORY.md`：记忆库入口与书写规则。
- `stages/`：按时间顺序保存阶段事实，文件名固定为 `taskN.md`。
- `summaries/`：按主题保存当前有效结论，只维护当前状态，不堆历史流水账。

## 默认读取顺序

1. 读取本文件；
2. 读取 `summaries/CURRENT.md`；
3. 仅在需要续接最近工作时读取最新 `stages/taskN.md`；
4. 根据任务按需读取 `summaries/` 中最相关的 1～3 个专题文件；
5. 只有需要追溯时才读取更早的 stage 或 Git 历史。

禁止默认批量读取所有 stage。

## Stage 文件规则

1. `taskN.md` 编号只增不改，不重排、不复用；历史阶段不为“看起来最新”而改写。
2. 一个相对完整、可独立说明目标与结果的开发阶段对应一个 task；零碎小修改不单独建 task。
3. Stage 主要回答“发生了什么”，只记录可核验事实、实际修改、验证结果、限制和后续影响。
4. 计划、候选方案与已完成事实必须分开。状态统一使用：`CONFIRMED` / `PLANNED` / `PROPOSED` / `UNKNOWN` / `SUPERSEDED`。
5. 不把宣传性表述、未经查新的创新结论、猜测或过期状态写成事实。
6. 涉及代码时优先记录关键文件、调用链、测试/实验结果；涉及高风险操作时记录回滚与影响范围。
7. 不提交密码、Token、Cookie、API Key、临时密钥或其他敏感凭据。

推荐模板：

```markdown
# Task N：阶段名称

状态：CONFIRMED

## 1. 阶段目标
## 2. 开始前状态
## 3. 本阶段实际完成
## 4. 关键设计与决定
## 5. 修改文件
## 6. 验证结果
## 7. 当前限制
## 8. 尚未完成
## 9. 对后续阶段的影响
```

## Summary 文件规则

- Summary 主要回答“现在是什么”。
- 同一事实只在最合适的一个 summary 中展开，其他文件只做必要引用。
- 架构变化、长期决策或阶段完成后，先写 stage，再压缩更新对应 summary。
- 旧结论失效时，用新 stage 记录变化，并把 summary 更新为当前结论；不要在 summary 中堆叠旧版本。
- Git 历史承担长期追溯职责，没有独立记忆价值的重复文档可以从当前树删除。

## 信息权威

当前真实代码/测试/命令输出 > 当前 Git 状态 > `summaries/CURRENT.md` > 专题 summary > 最新 stage > 更早 stage / Git 历史。

如记忆与实际仓库冲突，以实际仓库为准，并在本阶段结束后修正记忆。
